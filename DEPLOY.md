# Deployment

Supported topologies. **Option A is recommended** — it is simpler, avoids CORS
entirely, and keeps the SSE kline stream on a direct browser↔API connection with
no third-party edge in the middle. Options B and C split the frontend onto a CDN;
Option D swaps Render for Railway on the API side and applies to any of them.

Whatever the split, the API must run as a persistent process in an EU region.
Those two constraints are what rule most platforms out — see "Things that will
bite you".

---

## Option A — Single service on Render (recommended)

One Node process serves both `/api` and the built SPA. `render.yaml` in the repo
root is a Render Blueprint that encodes everything below.

### 1. Database (Neon, free)

1. Create a project at [neon.tech](https://neon.tech) — pick an **EU region**.
2. Copy the pooled connection string. It must end with `?sslmode=require`.

Supabase works identically; use its connection string instead.

### 2. Service (Render, free)

1. Push this repo to GitHub.
2. Render → **New → Blueprint** → select the repo. It reads `render.yaml`.
3. Set the one secret it cannot generate: `DATABASE_URL` (from step 1).
4. Deploy. The build runs `pnpm run build:deploy`, which builds the API, builds
   the SPA, and applies Prisma migrations.

`JWT_SECRET` is generated by Render automatically. Migrations run on every
deploy and are idempotent.

### 3. Verify

```
https://<your-service>.onrender.com/api/healthz   → {"status":"ok"}
https://<your-service>.onrender.com/              → the app
```

## Option B — Vercel (frontend) + Render (API)

Use this if you want the static frontend on Vercel's CDN. The browser then
talks to the API host directly, so CORS must be configured.

### Vercel

`vercel.json` already pins the build to the frontend only — the API server is
never typechecked or built there.

| Setting | Value |
|---|---|
| Framework preset | Other |
| Build command | `pnpm run build:web` (from `vercel.json`) |
| Output directory | `artifacts/crypto-heatmap/dist/public` |

Add one **build-time** environment variable:

```
VITE_API_URL = https://<your-api>.onrender.com
```

This is baked into the bundle at build time, so changing it requires a redeploy.

### Render (API only)

Same as Option A, plus:

```
CORS_ORIGIN = https://<your-app>.vercel.app
```

Without it the API refuses to boot in production when it is not serving the
frontend itself — that guard is intentional.

## Option C — Netlify (frontend) + Render (API)

Same shape as Option B, with Netlify instead of Vercel. `netlify.toml` in the
repo root encodes the build.

| Setting | Value |
|---|---|
| Build command | `pnpm run build:web` (from `netlify.toml`) |
| Publish directory | `artifacts/crypto-heatmap/dist/public` |
| Base directory | leave empty — the build runs from the repo root |

Add one **build-time** environment variable in Netlify → Site configuration →
Environment variables, then trigger a redeploy (it is baked into the bundle):

```
VITE_API_URL = https://<your-api>.onrender.com
```

On the Render API set `CORS_ORIGIN = https://<your-site>.netlify.app`.

Two things in `netlify.toml` are load-bearing:

- The `/*` → `/index.html` 200 redirect. Without it every route except `/` is a
  Netlify **"Page not found"**, because no file exists on disk for it — wouter
  routes client-side. A deploy with no `netlify.toml` at all 404s even on `/`,
  since Netlify then publishes the repo root, which has no `index.html`.
- `PNPM_FLAGS = "--frozen-lockfile --prod=false"`. The frontend's build
  toolchain (react, vite, tailwind) lives in `devDependencies`.

Do **not** proxy `/api/*` through a Netlify redirect. The edge buffers the SSE
kline stream, so the heatmap stalls instead of filling in progressively. Point
the browser straight at the API host with `VITE_API_URL`.

## Option D — Railway for the API

Railway can replace Render for the API in either Option A (single service) or
Options B/C (API only). It is a persistent container, not serverless, so the
in-process caches and the SSE stream work exactly as they do on Render.

Why prefer it over Render's free tier: Railway containers do not sleep. On
Render free, every 15-minute idle period costs a 30–60 s cold start *and* a full
kline refetch, because the cache dies with the process. The tradeoff is money —
Railway has no permanent free tier, so budget for the Hobby plan; check the
current pricing page rather than trusting this line.

`railway.toml` in the repo root encodes the build, the migration pre-deploy step,
the start command, the healthcheck and the single-replica constraint. Two things
it cannot set — do them in the dashboard:

1. **Region → `europe-west4`** (or any EU region). Railway defaults to
   `us-west1`, and Binance answers HTTP 451 to US IPs. A US region breaks the
   entire market pipeline, and the failure looks like empty data rather than a
   crash.
2. `DATABASE_URL` and `JWT_SECRET` (≥32 chars). Unlike Render, Railway does not
   generate secrets from a blueprint — generate the JWT secret yourself, e.g.
   `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

Also set, in the service variables:

```
NODE_ENV        = production
CORS_ORIGIN     = https://<your-site>.netlify.app
BINANCE_API_BASE = https://data-api.binance.vision/api/v3
```

`PORT` is injected by Railway and already honored in production
(`artifacts/api-server/src/index.ts`). The graceful SIGTERM shutdown the server
implements is what Railway sends on redeploy, so in-flight SSE streams close
cleanly.

For the database, Railway's own Postgres in the same EU region avoids Neon's
free-tier autosuspend and the cross-provider hop. Neon works fine either way —
just keep it in an EU region.

To serve the frontend from Railway too (single service, no CORS, no Netlify),
change the build command in `railway.toml` to `pnpm run build:deploy` and remove
`CORS_ORIGIN`. `app.ts` detects the built SPA and serves it automatically.

**Do not raise the replica count.** The kline cache, Binance proxy cache and
rate-limit buckets are per-process; a second replica doubles the Binance traffic
and splits the rate-limit accounting.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | **yes** | Postgres. Server exits at boot without it. |
| `JWT_SECRET` | **yes** | ≥32 chars. Server exits at boot if shorter/missing. |
| `NODE_ENV` | production | Enables the production guards. |
| `PORT` | auto | Injected by the platform; honored only in production. |
| `API_PORT` | no | Overrides `PORT`. Used locally. |
| `JWT_EXPIRES_IN` | no | Defaults to `7d`. |
| `CORS_ORIGIN` | separate frontend host | Comma-separated origins. |
| `BINANCE_API_BASE` | recommended | See the Binance note below. |
| `REDIS_URL` | no | Falls back to an in-process memory cache. |
| `VITE_API_URL` | separate frontend host | Frontend build-time only. |
| `STATIC_DIR` | no | Override the SPA path; defaults to the build output. |

## Things that will bite you

**Binance blocks US IPs with HTTP 451.** Any US-region host breaks the whole
market pipeline, because in production all Binance REST traffic is proxied
through our API (`/api/binance`). Deploy in Europe and keep
`BINANCE_API_BASE=https://data-api.binance.vision/api/v3` — the official public
market-data host, which tolerates datacenter IPs far better than
`api.binance.com`. This app only calls public endpoints, so nothing is lost.

**Render's free tier sleeps** after 15 minutes of inactivity; the next request
pays a 30–60 s cold start. The first load after a cold start also refetches all
klines because the cache is in-process. Acceptable for a private tool, not for
public traffic — Railway (Option D) is the paid way out.

**Do not run this API on serverless** (Vercel Functions, Netlify Functions, Lambda). The kline
cache, the Binance proxy cache and the rate-limit buckets are all in-process,
and the SSE stream runs for 30–40 s on a cold cache. Serverless would refetch
from Binance on every cold start and get the IP banned (HTTP 418).

**Neon free autosuspends.** The first auth request after idle takes a few extra
seconds. `/api/healthz` deliberately does not check the database, so an idle DB
never causes a restart loop.

**Secrets.** The repo root `.env` holds real local credentials and is gitignored —
confirm with `git ls-files | grep .env` (only `.env.example` files should
appear). Never set production secrets in a file; use the platform dashboard.

**Access gate.** The app is still behind the private access-code screen
(`src/components/auth/AccessGate.tsx`) before login. It is client-side only, so
treat it as a privacy curtain, not a security control.

## Testing the production build locally

```bash
pnpm run build:api
pnpm run build:web
NODE_ENV=production API_PORT=8090 node artifacts/api-server/dist/index.mjs
```

Then open `http://localhost:8090` — this is byte-for-byte what Option A serves.
